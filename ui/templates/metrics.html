A feature is the entitlement-checkable name on top of a meter. meterGroupByFilters narrows the meter, for example to one model, so each model can carry its own price and grant.

Endpoints that change state

The OpenMeter calls this PoC uses. The first two are driven by the form above; the rest are driven by the price editor and the seed scripts, or proxied straight through.

MethodPathWhat it changes
POST /api/v1/meters Creates a meter: aggregation, event type and counted JSONPath.
POST /api/v1/features Creates a feature bound to a meter, optionally filtered by a group-by value.
POST /api/v1/customers Creates a customer and its usage attribution (subject keys).
POST /api/v1/subjects/{subject}/entitlements Grants a metered entitlement: feature, usage period, issue-after-reset amount.
PUT /api/v1/subjects/{subject}/entitlements/{id}/override Replaces an entitlement with a new grant (the budget editor uses this).
POST /api/v1/subjects/{subject}/entitlements/{id}/reset Starts a new usage period at a given time, zeroing period usage.
POST /api/v1/plans/{key}/next Creates the next draft plan version.
PUT /api/v1/plans/{id} Rewrites a draft plan's phases and rate cards.
POST /api/v1/plans/{id}/publish Publishes the draft as the active version.
POST /api/v1/subscriptions/{id}/change Moves a subscription to another plan version (immediate timing).
POST /api/v1/events Ingests a usage CloudEvent; the metering relay prices it before forwarding.

Read-only lists come from GET /api/v1/meters and GET /api/v1/features. Creating a metric does not price it or grant it: add a rate card on a plan and an entitlement for a subject to make it billable.
